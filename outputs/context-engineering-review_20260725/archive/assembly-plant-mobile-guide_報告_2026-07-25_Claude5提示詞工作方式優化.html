工作方式優化檢視

依據：The New Rules of Context Engineering for Claude 5 Generation Models（已實際開啟驗證）
對照對象：WTF 全域設定制度＋Assembly_Plant_Mobile_Guide 實際工作紀錄｜2026-07-25

文章六條新規則（一句話版）

規則意思
規則 → 判斷刪掉可由常識推得的明確指令，留判準。Anthropic 刪掉 Claude Code 系統提示 80% 而無效能損失。
範例 → 介面設計不給使用示例，改把工具／腳本／檔案的「參數與欄位」設計得有表達力，模型自己會推。
前置載入 → 漸進揭露資訊按需載入，不全塞開場。
重複指令 → 單一位置指令只寫在工具描述處，不在系統提示重複。
CLAUDE.md 記憶 → 自動記憶模型自動保存相關資訊，設定檔不必當記憶體用。
簡單規格 → 豐富參考HTML 成品、程式碼、測試套件、rubric 都可直接當規格（designs work better than descriptions）。

你已經做對的

符合漸進揭露：GLOBAL.md 只放常規、長內容進 playbooks 按需開、skills lazy-load、_context 三檔制——正是文章說的 progressive disclosure，制度面超前多數人。

符合豐富參考：丟截圖標 UI 問題、丟參考 wav 定 TTS 聲線，都是「參考物勝過描述」的正確用法。

符合陷阱式教訓：lessons-learned 記的多是反直覺陷阱（如 zinc-100 白字隱形、snap 容器判斷），這正是新規則下值得留在 context 的內容。

建議調整（附實例：舊提示詞 vs 新提示詞）

1. 參考物一開始就給，不用形容詞迭代 改

實例：微台版 TTS。當時先用文字形容聲線，edge-tts 調參數失敗兩輪，最後丟出參考 wav 才收斂。

舊寫法（實際發生）「瀏覽器 TTS 可以換風格嗎，50歲台灣男性口音」→ 產出被退「一點也不台」→ 再補「要這 tts試聽_GeminiTTS_微台版v2」 新寫法「重現這個檔案的聲線：…/tts試聽_GeminiTTS_微台版v2.wav（50歲台灣男性、微台味、詞尾不轉台語）。驗收＝產出與參考檔並排播放給我比對。」

參考檔就是規格。形容詞（台、沉穩、親切）每個人解讀不同，檔案不會。

2. 素材照「介面欄位」給，用既有頁面當結構規格 改

實例：新增「空襲」展項。素材是一段自由格式的文字＋圖，AI 第一版把「車削」誤判成展品頁內的說明區塊，被退重做。

舊寫法（實際發生）「展品頁新增展示項目說明 1. 車削（文案）（圖）2. 互動機具…」→ 結構被誤判 新寫法「新增獨立展項頁，結構照『護廠行動』那一頁。欄位：名稱＝空襲；短述＝（可代擬）；內文＝…；大圖＝<路徑>；推薦展項＝護廠行動。」

這就是文章的「介面設計」：exhibits.ts 的欄位（名稱／短述／內文／圖／相關展項）本身就是最強的提示。照欄位給素材＋一句「照某頁」，結構零歧義。

3. 給驗收條件，不給步驟 保持並強化

實例：EN 導覽列修正。你列的是「症狀＋期望」（遮擋內容、不要兩行），沒有指定怎麼改——這是對的，讓模型自己找根因（實際根因是標題換行撐高 header，跟直覺不同）。

繼續這樣寫「英文版上方導覽列遮到內容、文字變兩行。驗收：三語言 header 都單行、不蓋到 hero。」＋一張截圖

4. 規則檔往「陷阱＋判準」收斂 中期整理

GLOBAL/AGENTS 內不少「禁止Ｘ」是新模型本來就會判斷的（聊天語氣、浮誇修飾這類可留判準一句，不必列舉）。文章示範：「never write multi-paragraph docstrings…」改成「match surrounding code」。

  • 保留：反直覺陷阱（Drive 不可原地 git、版控鐵律、zinc token 重映射）、判準（何時升級、何時算完成）。
  • 可精簡：行為列舉式禁令、與判斷力重疊的規則。
  • AGENT_SPEC：與其逐條圈「不准動哪些檔」，改給驗收 rubric＋測試（文章：test suites as specifications），範圍交給檔案結構本身約束。

5. HTML 輸出偏好：留一份範本檔勝過描述規則

之後若建 rules/html-preferences.md，與其寫形容（「沉穩、留白多」），不如放一個參考 HTML 檔路徑＋一句「照它的視覺系統」。

一句話總結

你的制度層（漸進揭露、教訓庫）已符合新規則；要調的是單次提示習慣——把「描述＋事後退件」換成「參考物＋介面欄位＋驗收條件」前置給足。
