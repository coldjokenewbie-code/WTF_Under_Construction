# /heart-beat — 定時心跳回報

用法：
- 對話中直接說「n 分鐘心跳」（例：「5 分鐘心跳」）— 套用到當前這批任務。
- `/heart-beat n [任務描述]` — 顯式啟動，n 為分鐘數。

來源：AGENTS.md「n 分鐘心跳」規則（2026-08-14 PO 裁定）。本 skill 是該規則的可操作化版本。

## 核心規則

任務全部完成、或使用者喊停之前，**每 n 分鐘輸出一句使用者看得見的文字**：「目前進度＋預估還要多久」。

**心跳判準：只呼叫排程／等待工具（ScheduleWakeup、Monitor 等），但該回合沒有輸出文字＝心跳失敗。** 心跳必須是回合裡實際打出來的一句話，不是工具呼叫本身。

## 執行機制

1. **啟動**：記錄起始時間。用 Bash 執行 `date +%s`，把結果當作 `last_beat_ts`；同時記下 `interval_sec = n*60`。不必寫檔，記在對話狀態裡即可（多輪對話靠自己追蹤，不依賴外部計時器）。
2. **推進中**：每次要執行下一批動作前，先用 `date +%s` 讀目前時間，減去 `last_beat_ts`：
   - 差值 `< interval_sec` → 不用心跳，正常做事。
   - 差值 `>= interval_sec` → **先輸出一句心跳文字**，再繼續做事；輸出後把 `last_beat_ts` 更新為現在。
3. **心跳文字格式**：一句話，含兩個要素——現在做到哪、預估還要多久。例：
   - 「目前在跑第 3/5 個模組的測試，預估還要 10 分鐘。」
   - 「素材生成中，已完成 4 張，剩 2 張，預估 5 分鐘內完成。」
4. **任務完成當回合**：不用心跳格式，直接照一般結束流程回報結果即可。
5. **停止條件**：任務全部完成，或使用者明確喊停（如「不用心跳了」「先停」）。

## 已知失敗模式（不要踩）

- **只排程不出聲**：呼叫 ScheduleWakeup／Monitor 等待工具、但該回合沒有任何文字輸出 → 使用者看不到任何進度，視為心跳失敗。這類工具本身不算心跳。
- **單一長工具呼叫吞掉心跳窗口**：若某一步驟（大型 Agent 派工、長跑 Bash、大量檔案處理）預估會超過 n 分鐘且中途無法插入文字，先在啟動該步驟前告知使用者「這步驟預估約 X 分鐘，期間心跳會延後到它結束」，避免使用者誤以為卡住。
- **多任務並行時心跳失焦**：用 Agent fork／Workflow 派多個子任務時，心跳由主對話 agent 統一彙總各子任務進度回報一句，不是每個子 agent 各自對使用者心跳。
- **心跳內容空洞**：避免只寫「處理中」而不給進度或時間估計；沒有具體進度可講時，至少講清楚卡在哪個步驟、原因是什麼。
