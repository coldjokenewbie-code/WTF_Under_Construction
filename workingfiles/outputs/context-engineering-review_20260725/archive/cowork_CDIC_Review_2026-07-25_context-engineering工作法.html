二、核心：「介面設計取代範例」——五個真實工作實例

文章核心主張：範例會限縮模型的探索空間；改用結構（枚舉、schema、參數、機檢）傳達用法。以 Todo 工具為例：把 status 做成 pending | in_progress | completed 枚舉，模型自然懂怎麼用，不需要示範。

實例 1｜派工回報格式（delegation-templates.md 的「通用回報合約」）

以前：prose 合約＋範例式描述 
回報要求：
- 第一行＝一句話結論（完成／失敗／部分完成＋主因）。
- 只回結論與判斷，每個事實附 檔案:行號。
- 回報總長 ≤120 行。……（原文照貼進每份 prompt）
現在：schema 枚舉，讓結構自己說話 
用 Agent/Workflow 的 structured output schema：
{ "status": "done | failed | partial",
  "conclusion": "一句話",
  "facts": [{ "claim": "...", "evidence": "檔案:行號" }],
  "artifacts": ["路徑"],
  "blockers": ["失敗才填"] }

枚舉本身就傳達了「失敗要老實說」「事實要附證據」，不必再用文字叮嚀；且回傳保證可機器解析，驗收腳本直接吃。今天派「V3→USB 同步」agent 已這樣做（規則式 prompt＋結構化回報），可回溯驗證。

實例 2｜中翻英審稿 docx（translation-bilingual-docx.md）

以前：拿成品當範本 
「照 B 區成品這樣做：
outputs/V1/B_kiosk/archive/B_doc/
W英文審稿_B區…v3_20260622.docx
＋146 行 SOP 逐步驟讀完再動工」
現在：輸出介面＋可勾 rubric 
輸出介面：同格中文下加英文、不增欄；
三欄淨文中文＝#00B0F0；strike＝不譯不刪。
驗收 rubric（缺一即 FAIL，逐條可機檢）：
□ 缺譯即中止（missing keys=0）
□ testzip()=None、圖片數與備份一致
□ PDF 首頁目視：中上英下、藍黑正確
成品檔＝歧義時才查的參照，不是範本。

差別：範本要模型「模仿」，介面要模型「滿足規格」。模仿會連範本的偶然特徵一起抄（那份 docx 的欄數、那區的年代格式），規格才可跨區重用——E/B/C/D 四區欄數各不同，正是吃過這個虧才在 SOP 寫「用欄標題判定勿寫死欄索引」。

實例 3｜E 區「流動的河」背景（07-08 三輪退改教訓）

以前：純文字形容意象 
「背景要有流動的河的感覺」
→ AI 各自解讀成噪點/漸層/亮暗帶
→ PO 看了「很髒」，三輪退改
現在：文章規則⑤「豐富參照」三件套 
①參考圖 1-2 張（意象定錨）
②可跑的 HTML mockup（構圖定錨）
③評分 rubric：
  - 乾淨度：無噪點顆粒感
  - 流動感：曲線位移、非亮度閃爍
  - 對標：與參考圖並排合成一張比對

你 07-08 已自行歸納出「抽象材質先要參考圖」，文章等於官方背書並加碼：參照物要從文字升級到 HTML 構件＋rubric。你們的「並排合成一張圖做 A/B」（07-02 教訓）就是 rubric 的雛形。這條與「範例限縮探索」不衝突——見第三節判準。

實例 4｜溝通文風規範（AGENTS.md 溝通原則節）

以前：禁止式長列表 
禁止：確認語、重述請求、總結、過渡語、
安撫、附和、認錯表演、預告、「您」、
踩坑、閉環、賦能、抓手……（20+ 條）
現在：一句結果式＋機檢介面 
prose 端一句話：
「回應只含資訊、推論、判斷；
 結構＝結論→依據→待決。」
細部禁詞 → 全交 ody-lint stop hook
（違規攔截重寫，模型永遠學得到）

文章的 before/after 同型範例："DO NOT add comments..." → "Write code that reads like the surrounding code"（禁止式→結果式）。你的 ody-lint 正是「把規則做成介面」的正例——本 session 我就被它攔過一次「沒問題」，這比 prose 裡多寫十條禁詞都有效。建議方向：prose 瘦身、機檢擴充。

實例 5｜UI 修改指令（作業慣例「字體每次只調 1-2px」）

以前：用細則防 AI 亂改 
「字體大小每次只調 1-2px；
幅度較大要先確認；
禁止連帶修改沒被要求的元素」
現在：把可調項做成介面，跳過自然語言 
B 區 ?edit=1 tweaks 面板＝實體案例：
字級/間距/位移做成範圍參數，
PO 拖拉即所見即所得，寫回 HTML。
→「調字體」這類提示詞整類消失。

「介面設計」的終極形態：讓高頻、低歧義的需求根本不經過提示詞。你們已在 A/B 區編輯器、E 區 demo tweak（20-150 可調）做到，值得明文化成慣例：同類修改被要求第三次＝做成參數面板（與記憶「連改 3 次即建需求彙整」同構）。

三、那「提供範例」什麼時候仍然對？

仍該給範例/參照為什麼
glossary 術語表（展版中英文案_專有名詞參照.xlsx）這是權威資料不是範例——它定義唯一正解，不存在「限縮探索」問題
視覺參考圖、PO 手改稿品味與意象無法 schema 化，範例是意圖的最高保真載體
對抗歧義的單一錨點（如「同格中文下加英、不增欄」附一格截圖）一個錨點消歧義 ≠ 一整份成品供模仿
一句話判準：傳「結構與規則」用介面（schema/枚舉/rubric/機檢），傳「品味與意象」用參照（圖/mockup/手改稿）。錯位才是問題：拿整份成品傳規則（實例 2）、拿文字傳意象（實例 3）。
